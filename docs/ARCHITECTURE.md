# Architecture

The Avenx.js Developer Dashboard is one static site that shows the API reference, the test coverage and the performance benchmarks of [Avenx-JS/avenx-js](https://github.com/Avenx-JS/avenx-js). It replaces three repositories, three GitHub Pages sites and the two publishing workflows that fed them. This document records what was there before, how the replacement works and why it is built the way it is.

## 1. What it replaces

The inventory below was taken on 2026-11-23 from the repositories themselves, their workflow files and their run history. It is the basis for every decision in section 4.

| | API reference | Test coverage | Benchmarks |
| --- | --- | --- | --- |
| Domain | `dev.avenx-js.com` | `coverage.avenx-js.com` | `benchmarks.avenx-js.com` |
| Repository | `Avenx-JS/dev-docs` (branch `master`) | `Avenx-JS/test-cov` (`master`) | `Avenx-JS/bench-results` (`master`) |
| Generated by | `avenx-js/.github/workflows/dev-docs.yml` | `avenx-js/.github/workflows/quality-results.yml`, job `test-coverage` | `quality-results.yml`, job `benchmarks` |
| Command | `npm run docs` → `jsdoc -c jsdoc.json` (default template) | `npm run test:coverage` → `c8 --reporter=text --reporter=html npm test` | `npm run bench:report` → `node benches/run.js --json > bench-results/results.json` |
| Trigger | every push to `avenx-js` `main` | Saturdays 10:00 UTC | Saturdays 10:00 UTC |
| Transport | `rsync` into a checkout of the target repo, commit, push with the `PAT_TOKEN` secret | same | same |
| Hosting | `static.yml` in the target repo deploys the whole repo to Pages on push to `master` | same | same |
| Content | 318 HTML pages: 46 class pages, 114 module pages, 158 source views, `index.html` (README), `global.html` | c8 HTML report (index, per-directory and per-file annotated source) plus 863 raw V8 dumps in `tmp/` | one file, `results.json`; there is no HTML page |
| History | git history only (130 commits) | git history only (14 commits, 12 with a report) | git history only (15 commits, 14 with results) |

State of the legacy pipelines at the time of the migration:

- **API reference stale since 2026-09-16.** JSDoc logs an `ERROR` for TypeScript-style type expressions (`{a?: T}`, `import('…').T`, `{…}[]`) and then exits with code 1, although its output is complete. The workflow treats the exit code as fatal, so every run since then failed before publishing. 56 such errors exist at the time of writing.
- **Weekly quality run red in 4 of the last 8 weeks.** On 2026-10-17 and 2026-10-24 no coverage report was published, on 2026-10-31 and 2026-11-21 no benchmark results (the commits in the two repositories show which job got through). On 2026-11-21 `render-scenarios.bench.js` crashed in `ComponentParser.parse`, `benches/run.js` exited 1 and the job stopped before publishing.
- **Test coverage published its raw inputs.** c8 keeps the V8 coverage dumps in `coverage/tmp/`; the rsync copied them to the public repository (863 files).
- **Cross-repository pushes** need a personal access token with `repo` scope, stored as `PAT_TOKEN` in `avenx-js`.

Nothing is pushed to another repository. The framework repository is only read, and it is public, so the default `GITHUB_TOKEN` is enough.

### Repository layout

| Path | Purpose |
| --- | --- |
| `.github/workflows/dashboard.yml` | The only workflow: test, collect, record, build, check, deploy, report. |
| `scripts/collect.js` | Runs the three upstream commands in a checkout and writes `.cache/collected/`. |
| `scripts/record.js` | Appends coverage and benchmark results to `data/*/history.json`. |
| `scripts/build.js` | Renders `dist/` from `data/` and `.cache/collected/`. |
| `scripts/check-site.js` | Fails on any broken internal link, anchor or redirect target. |
| `scripts/status.js` | Writes the job summary; exits 1 when a collection step failed. |
| `scripts/serve.js` | Local preview server (development only). |
| `scripts/lib/parse.js` | Pure parsers for c8, istanbul HTML, test runner, benchmark and JSDoc output. |
| `scripts/lib/docs-model.js` | Reduces `jsdoc -X` doclets to the model the API pages use. |
| `scripts/lib/history.js` | Reads and writes the history files. |
| `scripts/migrate/import-legacy.js` | One-time import of the legacy history (section 5). Not used by the build. |
| `src/` | Page templates (`pages/`), layout, charts, CSS and the small client script. |
| `data/` | Committed data: coverage and benchmark history, legacy page names. |
| `test/` | Unit tests and a build smoke test (`npm test`). |

## 3. Data

### Collected per run (`.cache/collected/`, not committed)

| File | Content |
| --- | --- |
| `meta.json` | Upstream repository, commit, commit date and subject, package version, Node version, and per step: status, exit code, duration, reason. |
| `docs.json` | Modules, symbols (classes, functions, members, constants, typedefs …) with descriptions, parameters, returns, throws, examples, source file and line; the rendered README; JSDoc diagnostics; statistics. |
| `coverage.json` | Totals, per-directory and per-file statements, branches, functions and lines (from c8's `json-summary` reporter), and the test summary (files total/passed/failed, failing files). |
| `coverage-report/` | The c8 HTML report, unchanged, without `tmp/`. |
| `benchmarks.json` | `benches/run.js --json` output with a status per benchmark, the crash report, the file header description of each benchmark and the pull-request gate thresholds from `benches/regression-gate.js`. |
| `logs/` | stdout and stderr of every command. Uploaded as the `collection-logs` artifact. |

### Recorded history (`data/`, committed)

`data/coverage/history.json` and `data/benchmarks/history.json` share one envelope:

```json
{ "schemaVersion": 1, "runs": [ { "recordedAt": "ISO date", "source": { … }, … } ] }
```

- Coverage run: `total` and `directories` (each with `statements`, `branches`, `functions`, `lines` as `{ covered, total, pct }`) and `tests` (`{ total, passed, failed }`, `null` for legacy runs, whose reports did not contain it).
- Benchmark run: `results`, the rows of `results.json` (`file`, `name`, `totalTime`, `avgTime`, `ops`, `timestamp`) plus `status` (`ok`, `failed`, or `unknown` for legacy runs).
- `source.kind` is `legacy` (with `legacyCommit`, the commit in the legacy repository it was imported from) or `workflow` (with `upstreamCommit`, `version`, `node`, `runId`).

`data/legacy/dev-docs-pages.json` lists the page names of the legacy API site so old links can be redirected (section 4, D9).

### Published data

Besides the pages, the site serves machine-readable files: `benchmarks/results.json` (the latest run in exactly the legacy `results.json` shape), `data/coverage-history.json`, `data/benchmarks-history.json` and `data/latest.json`.

## 4. Decisions

**D1 — A static site built by a plain Node script, without dependencies.** The dashboard itself installs nothing: no framework, no chart library, no markdown parser of its own. Pages are template literals, charts are SVG generated at build time. The only tools that run come from the framework's own `node_modules` (JSDoc, markdown-it, c8), which `npm ci` installs anyway to run the tests. Dependabot has nothing to update here, and there is no second lockfile to keep in step with the framework's. The trade-off is that templates are hand-written HTML; with four page types this stays small.

**D2 — Run the framework's own commands in a read-only checkout.** The collector runs `jsdoc -c jsdoc.json`, `npm run test:coverage` and `node benches/run.js --json` exactly as the legacy pipelines did, with the configuration that lives in the framework repository. A change to `jsdoc.json`, the test runner or a benchmark takes effect without touching the dashboard. Because the data is produced where it is published, the cross-repository push and the `PAT_TOKEN` it needed go away.

**D3 — Commit a compact history; regenerate everything else.** The legacy repositories kept history only as git commits of overwritten files. The dashboard keeps it as data: one entry per weekly run in `data/*/history.json` (about 10 KB per coverage run, 4 KB per benchmark run), committed by the workflow with `GITHUB_TOKEN`. Large outputs (the c8 HTML report, 13 MB; the JSDoc doclets, 18 MB) are regenerated on every build and never committed. Alternatives considered: downloading the previous run's artifact (expires, adds API calls) and reading the history back from the deployed site (a bad deploy would lose it).

**D4 — A failing step is reported, deployed, then fails the run.** The legacy pipelines aborted on a non-zero exit, which left the sites silently stale. Now each step's status is recorded; the dashboard shows failing test files, crashed benchmarks and JSDoc errors on the affected page and on the overview; the site is deployed; and the final `upstream-status` job fails the run. A JSDoc exit code of 1 with complete output counts as success with errors listed on *Documentation health*, since the errors only drop the unparseable type from a signature. The `benches/run.js` comment that asks for crashes to be a red build rather than a missing row is honoured on both counts: the run is red and the row says "crashed".

**D5 — Cadence.** The weekly slot of `quality-results.yml` (Saturday 10:00 UTC) is kept for recording, so the history continues at the same rhythm. The API reference used to update on every push to the framework; a workflow in this repository cannot be triggered by another repository's push without adding a token and a dispatch step there. A daily build at 03:30 UTC replaces it (at most one day of delay), plus a build on every push to this repository and on manual dispatch.

**D6 — Benchmarks run only when recording.** Daily builds collect the API reference and coverage (the c8 HTML report has to be regenerated for every deploy) but not the benchmarks: the benchmark page is built from the recorded history, so a daily run would add a minute of runner time and numbers that are not kept. A manual run with `record: true` measures and records outside the schedule.

**D7 — The API reference is rendered from JSDoc's data, not its default template.** `jsdoc -X` produces the same doclets the default template rendered. The dashboard selects them with the template's rules (no undocumented, `@ignore`d or `@private` doclets; the framework's `jsdoc.json` does not enable `private`) and renders them in the dashboard's design: module index, module pages, class pages, members with parameters, returns, throws, examples, `@see` and inherited/overrides information, `{@link}` resolution and a client-side symbol search. The legacy source views are replaced by links to the file and line on GitHub at the exact commit the reference was built from. Two cleanups that differ from the legacy output: a class JSDoc records as a member of itself is shown as top-level, and ES private methods (`#name`), which JSDoc emits without a name, are left out like other private members.

**D8 — Coverage: own summary, c8's line view.** The coverage page is built from c8's `json-summary` (derived from the same raw data with `c8 report`, so the suite runs once). The per-file annotated source is c8's own HTML report, published unchanged under `/coverage/report/` and linked from every directory and file. Colours follow c8's default watermarks (≥ 80 % good, 50–80 % warning, < 50 % critical), as the legacy report did. The trend chart leaves out statements because c8 counts them per line, so they equal lines in every recorded run.

**D9 — Old links keep working.** GitHub Pages serves `404.html` for unknown paths. It carries a map from every page name of the legacy API site (`AvenxApp.html`, `module-lib_bundler_emit.EmitError.html`, `lib_core_x.js.html`, …) to the new page, computed with JSDoc's file-naming rule. Of the 317 legacy pages, 238 map to their page in the dashboard and 79 source views of files without a module page map to the file on GitHub; a symbol that is no longer found by name would fall back to a search for it. This works when the dashboard takes over `dev.avenx-js.com`. `benchmarks/results.json` is kept in the legacy shape for anyone reading it.

**D10 — "Documented declarations".** The API overview shows the share of classes and functions in static, instance or global scope that carry a doc comment (inner helpers and plain member assignments are excluded; JSDoc's duplicate doclets for one ES export count once; constructor artefacts are skipped). At the time of writing: 1,341 of 1,418 (94.6 %).

**D11 — Charts.** Line charts are SVG with a fixed height and stretched geometry (non-scaling strokes), with HTML axis labels and markers, so they stay legible from phone to wide screen. Every chart has a legend for two or more series, a hover tooltip, and a data table. The series colours were checked with a colour-vision-deficiency validator in light and dark mode. Benchmark changes below 10 % are not coloured, because single runs on shared runners move that much on their own (`benches/regression-gate.js` documents A/A spreads of 10–40 %).

## 5. History migration

`scripts/migrate/import-legacy.js` walked the legacy repositories once and wrote:

- 14 benchmark runs (2026-06-15 to 2026-11-14) from the commits that changed `results.json` in `Avenx-JS/bench-results`; the run time is the earliest row timestamp.
- 12 coverage runs (2026-06-15 to 2026-11-21) by parsing the summary and directory table of every committed `index.html` in `Avenx-JS/test-cov`.
- 318 legacy page names from `Avenx-JS/dev-docs`.

Each imported run names the legacy commit it came from. Not migrated, deliberately: the 863 raw V8 dumps in `test-cov/tmp/` (inputs to the report, not results), the per-file coverage of past runs (only the latest per-file state is shown, as on the legacy site), and the stale JSDoc HTML of 2026-09-16 (superseded by the reference built from the current source).

## 6. Working on the dashboard

```bash
git clone https://github.com/Avenx-JS/avenx-js ../avenx-js && (cd ../avenx-js && npm ci)
npm run collect -- --upstream ../avenx-js     # ~2 min; --only docs for the API reference alone
npm run build && npm run check
npm run serve                                 # http://localhost:4173/
npm test
```

Without a collection the site still builds from the recorded history; pages say what is missing. Do not run `npm run record` locally: numbers from a laptop do not belong in the history measured on CI runners.

**Adding an area** means a step in `collect.js` that writes one JSON file, a page module in `src/pages/`, an entry in the navigation in `src/layout.js`, and, if it has history, a `record.js` entry.

## 7. Known limitations

- Upstream problems are shown, not fixed: at the time of writing 4 test files fail, `render-scenarios.bench.js` crashes and JSDoc reports 56 errors and 40 warnings. They are issues in `avenx-js`.
- Absolute benchmark numbers come from one run on a shared GitHub runner and are noisy. The pull-request comparison (`benchmark-compare.yml` in `avenx-js`) remains the place to judge a single change.
- The API reference lags the framework's `main` by at most a day (D5).
- GitHub announced the end of Node 20 for actions; the workflow uses the same action versions as `avenx-js` and should be bumped together with it.
